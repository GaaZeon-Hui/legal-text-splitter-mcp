Architecture Approaches

Three ways to structure the UI + Service integration

A

Single Process — Service Layer Pattern

Everything runs in one Python process. NiceGUI calls a local SplitService class that wraps the existing analysis modules. The class has the same interface as the future remote service (async methods, JSON I/O), but executes locally. When the external service is ready, swap the implementation from LocalSplitService to RemoteSplitService — same interface.

Pros

  • Fastest to develop right now
  • No network overhead for local use
  • Interface abstraction ready for future migration

Cons

  • CPU-heavy analysis blocks the NiceGUI event loop (must use asyncio.to_thread)
  • Service not independently deployable yet
B

Dual Process — FastAPI Service + NiceGUI Client

Two separate Python processes: a FastAPI service on port 8001 that wraps the full pipeline, and NiceGUI on port 8080 that calls it via httpx. Both can be started from one launcher script. Full separation from day one.

Pros

  • True process isolation
  • Service independently testable via curl / Swagger
  • No event loop blocking risk

Cons

  • Two servers to manage in dev
  • HTTP serialization overhead
  • Need to handle service unavailability
C

Single FastAPI — Mount NiceGUI

One FastAPI app serves both. /api/split endpoints are plain FastAPI routes; /* routes are NiceGUI pages, mounted via app.mount(). The API and UI share one process but are separated by route namespace.

Pros

  • Single process, single port
  • API endpoints auto-documented (Swagger)
  • Clean migration path to separate service later

Cons

  • Still shares the event loop (same blocking risk as A)
  • NiceGUI mounted under FastAPI has known quirks
  • Coupling at the process level
